Why this one

The domain is obvious, so none of your effort goes into figuring out what the thing is supposed to do. All of it goes into Go. You get request handling, routing, JSON, a database, connection lifecycle, error handling, and shutdown — which is most of what a service is.

This is the base. There will be follow-on exercises that build on this same codebase rather than starting over: a CLI against the same database, concurrency and background work, caching, middleware, gRPC, and a few others. Each one lands better if the foundation underneath it is something you wrote yourself, so it's worth being unhurried here.

The API

RouteWhat it does
POST / Takes {"url": "https://…"}. Generates a code, saves it, returns the code and the full short URL. If the body includes an optional code field, use that as a vanity slug instead of generating one.
GET /{code} Looks up the code and redirects 301 to the target. 404 if there's no such code.
GET /api/urls/{code} Returns the record as JSON — target, created time, hit count, last accessed.
DELETE /api/urls/{code} Removes it. 204 on success, 404 if it wasn't there.
GET /healthz Returns 200. No database call — this one answers whether the process is alive, not whether the database is.

Generated codes are eight random alphanumeric characters unless you have a reason to prefer something else. Vanity slugs will collide eventually, so decide what that response looks like.

The data

One table. At minimum code as the primary key, plus target_url, created_at, hit_count, and last_accessed_at. Types and anything extra are yours to pick. Commit the schema as a plain .sql file rather than letting anything auto-migrate it.

Every redirect bumps hit_count and touches last_accessed_at, which means every read now carries a write. Doing it inline in the handler is the simple answer and it's a defensible one. Pushing it onto a channel and draining it in a background goroutine is the other answer, and it drags in questions about what happens to buffered writes at shutdown. Either is fine — pick one and write a paragraph in the README about why.

How it's shaped

Three layers, each one only talking to the one below it. The names are conventional rather than meaningful, so here is what they actually refer to:

A browser, curl, whatever is calling you
crosses this line: an HTTP request

handler

The only part that knows it's on the web. Reads the request, pulls out the path parameter or decodes the JSON body, hands plain Go values downward. Takes back a result or an error and turns it into a status code and a response body.

Knows: HTTP verbs, status codes, JSON encoding. Doesn't know: that a database exists.

crosses this line: plain Go values — a URL string, a code, a struct

service

The rules of the thing. Generates the code, validates that a URL is a URL, decides what happens when a vanity slug is already taken, decides whether a redirect counts as a hit. If you swapped HTTP for gRPC tomorrow, or Postgres for a text file, this layer would not change.

Knows: what a short URL is and what the rules are. Doesn't know: HTTP or SQL.

crosses this line: "save this" / "find this one" / "delete it"

repository

The only part that speaks SQL. Takes a request for a record, runs the query, scans the rows into a struct, hands it back. Every query in the codebase lives in here and nowhere else.

Knows: tables, columns, drivers, sql.ErrNoRows. Doesn't know: HTTP, or why anyone wants this record.

crosses this line: SQL
MySQL or Postgres
The one shortcut to avoid: a handler reaching straight for the database because it's three lines shorter that way. The moment that happens the layers stop meaning anything, and the interface work below stops being possible. If you find yourself wanting to, that's usually a sign the service layer is missing a method.

Structs and interfaces

Both are required, and the architecture above is what makes them natural rather than ceremonial.

Structs

Define a real ShortURL struct and pass it around. Not map[string]any, not a fistful of loose string parameters. Scan database rows into it, encode it to JSON out of it, and use struct tags to control the JSON field names. Your other structs come out of the layering: each layer's dependencies live on a struct, and its methods hang off that struct rather than floating as package-level functions with globals behind them.

Interfaces

The service layer must depend on an interface, not on your concrete Postgres or MySQL repository. Something along these lines:

type Store interface { Save(ctx, ShortURL) error; ByCode(ctx, string) (ShortURL, error); … }

The service takes a Store. main is what decides that the Store is in fact the SQL implementation, and wires it in. Define the interface in the package that uses it rather than the package that implements it — that's the Go convention and it's the opposite of what Java or C# would have you do.

Keep it small. If your interface has eleven methods you've described a class, not an interface. The payoff shows up in the test section: with the service depending on Store, you can hand it a fake and test the rules with no database running anywhere.

What you can pull in

RoutingStdlib net/http. The Go 1.22+ ServeMux does method matching and path parameters, so there's no need for chi or gorilla here.

ORMFair game, but be able to say why you reached for it on any given query. Given your SQL, the interesting answer is probably a split: ORM for the boring CRUD, raw queries where you actually want control.
Everything elseStandard library.

If you do use an ORM, write the hit-count update both ways and put a short note in the README on which one you'd ship and why. Worth actually looking at the SQL the ORM generates before deciding.

Go things to get right

Context

context.Context starts at the handler and travels all the way into every database call. No query without one. This is the mechanism by which a cancelled request stops doing work instead of finishing a query nobody is waiting for.

Graceful shutdown

Catch SIGINT and SIGTERM with os/signal, cancel a root context, let in-flight requests finish, then close the database pool and exit. This is the one that usually takes the longest, and it's the one that teaches the most — channels, context cancellation, and ordering all show up at once.

Errors

Wrap with fmt.Errorf("doing the thing: %w", err) as errors travel up. log.Fatal belongs in main and nowhere else. The bar is that a single log line tells you where it happened and why, without opening a debugger.

Config

Environment variables read with os.Getenv, sensible defaults, no config library, no connection strings in the source. DATABASE_DSN, PORT, and BASE_URL at minimum.

AI ground rules

The value here is entirely in having written it, so the line is drawn around composition rather than around looking things up.

Go ahead

  • Syntax and names of things — how to declare a slice, what %w does, the signature of http.HandlerFunc, what sql.ErrNoRows is called.
  • Idiom questions — "what's the Go way to represent an optional value", "should this be a pointer receiver", "is this the normal way to structure a repository interface".
  • Ordinary editor autocomplete: symbol names, imports, method completion.

Not this

  • Asking for a function, a handler, a struct, or any block of logic to be written for you.
  • Pasting a requirement from this page and asking for an implementation.
  • AI autocomplete — Copilot, Cursor, Tabnine, anything that finishes more than a symbol name.

If you can't explain a line in your own words without looking at it, you didn't write it.

Tests

At minimum, a table-driven test over the code generator: right length, right alphabet, no duplicates across a decent number of runs.

The one worth doing properly is the service layer against a fake Store. Write a struct that satisfies the interface and returns whatever you tell it to, hand it to the service, and test the vanity-slug collision path and the not-found path with no database involved. That's the moment the interface stops being a formality.

Done looks like

  • A server binary that starts, serves, and shuts down cleanly on Ctrl-C.
  • schema.sql in the repo.
  • A README: how to run it, what env vars it needs, the sync-versus-background note on hit counting, and the ORM note if that applies.
  • go build ./... and go vet ./... clean.

Once this is standing up, the follow-on exercises attach to it directly, and by then most of the Go you need for real work will already be under your hands.
